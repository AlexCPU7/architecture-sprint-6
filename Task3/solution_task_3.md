# Переход на Event-Driven архитектуру

## Постановка проблемы и требования

Сервисы core-app и ins-comp-settlement получают данные о доступных продуктах через REST API сервиса ins-product-aggregator. В момент вызова он:
- запрашивает информацию из всех страховых компаний (сейчас их пять),
- агрегирует её в единый список,
- возвращает этот список в рамках того же синхронного запроса.

Чтобы ускорить работу сервисов, при изначальном проектировании команда решила хранить локальные реплики данных о продуктах и тарифах в сервисах core-app и ins-comp-settlement.

Сервис core-app осуществляет запрос к ins-product-aggregator раз в 15 минут, а ins-comp-settlement — раз в сутки (ночью), при формировании реестра оформленных страховок. Иногда команда сталкивается с ошибками взаимодействия между этими сервисами. Они связаны с задержками ответов или ошибками при взаимодействии с API страховых компаний.

Дополнительно сервис ins-comp-settlement раз в сутки осуществляет запрос в core-app по REST API для получения всех оформленных за день страховок. Эти данные он использует. 

В ближайшее время InsureTech планирует подписать агентское соглашение ещё с пятью страховыми компаниями. Вам предстоит спроектировать решение, которое устранит текущие проблемы.

## Технологические решение
Текущая схема работы:
[InsureTech_C4_сontainer-diagram.drawio.xml](InsureTech_C4_%D1%81ontainer-diagram.drawio.xml)

При текущей архитектуры мы сталкиваемся с несколькими проблемами:
- Общение между сервисами осуществляется через REST API, что приводит к высокой связанности системы.
А так же, при увеличении числа пользователей, увеличится отъем запросов, что в свою очередь спровоцирует нагрузку на сервисы и базу данных.
- Высокая нагрузка на сервис core-app. Сервис core-app является фактически центральным сервисом, через которого проходят основные операции.
Из-за этой связи, данный сервис может стать бутылочным горлышком при повышении нагрузки на всю систему.
- Получение данный в системе и отправка пользователю, не такое быстрое как могло бы быть.
У нас в системе одна реплика базы данных и отсутствуют кэш.
А без этих технологий взаимодействие с базой данных будет не такое быстрое, как могло бы быть.
- В сервисе ins-product-aggregator интеграция со страховыми компаниями, реализована не совсем корректно.
Проблема в том, что взаимодействие со страховыми компаниями осуществляется через протоколы REST/SOAP/GraphQL.
Что из-за этого возможны задержки в получении информации о тарифах.
И в свою очередь из-за этого будет страдать сервис core-app, так как он будет ждать ответа

Риски и возможные последствия:
- Значительные задержки отклика при росте числа пользователей.
- Трудности с горизонтальным масштабированием, особенно для core-app.
- Слабая устойчивость к сбоям из-за высокой связанности сервисов.
- Низкая гибкость при резком увеличении нагрузки, особенно во время массового оформления страховок.

Для того, что бы решить данные проблемы и минимизировать риски, необходимо провести следующие улучшения:
- Переход на Event-Streaming для ключевых взаимодействий.
Вместо REST API использовать очереди сообщений, такие как например Kafka или NAT.
И использовать их для обмена данными между сервисами core-app, ins-product-aggregator и ins-comp-settlement.
- Внедрение паттерна Transactional Outbox. 
При создании страховки сначала сохранять данные в таблицу Outbox в core-db.
Затем инициировать обработку событий через Event-Streaming.
Это предотвратит потерю данных при возникновении сбоев.
- Добавление в систему использование кэша.
Добавить например redis, для хранения тарифов страховых компаний, и обновлять эти данные раз в сутки.
Благодаря кэшу, мы снизим нагрузку на бд, на взаимодействие между сервисами и повысим скорость работы всего процесса оформления заявки во всей системе.
- Подробить core-app на несколько микросервисов. Необходимо разгрузить данной сервис, для того, что в случае необходимости его можно было масштабировать, и что бы избавиться от эффекта узкого горлышка.
